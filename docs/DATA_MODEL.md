# Data model and migration plan

**D22 data boundary:** Railway remains the current adult/internal database, with actual latest dashboard state still requiring a fresh read-only inventory and protected backup; it must **not** be modified for D22. The owner selected a **synthetic-only COPY** into a new Neon Free Frankfurt database named exactly `desloop_synthetic_stage`, not yet created/imported/verified. Migration 005 remains **unapplied on Railway** and outside automatic pre-deploy; source now permits a separate, operator-approved **direct-Neon** run after source/target parity, alongside the pre-existing named-disposable loopback path. A SQL-created limited runtime role/grants are distinct from restore-owner credentials. No Neon migration or real-person record has been verified. FND-01's public catalogue is a static versioned projection, not visitor data/progress. [D22 runbook](RENDER_NEON_SYNTHETIC_STAGE_D22_2026-11-01.md).

**Client follow-up (31 October):** STU-CORE-UI-01 and later local-only UI-02 added **no new tables or migration**. React sends bounded JSON, a stable request ID, base revision and existing asset IDs to the existing server contract; owner IDs, format validation, immutability, integrity and learning credit remain server/DB-owned. UI-02's unsaved text/base and uncertain intent are **volatile account-bound tab memory only**, cleared on sign-out/account change/exit; a fresh authenticated project GET must succeed before showing any held text. It is not offline backup or a DB record. Browser QA separately migrated 001–003/005 on a **fifth named disposable loopback DB**, not Railway. Missing erasure/retention/backup remains a real-user blocker.

**Public content projection:** `scripts/build_public_catalog.py` allowlists `version`, nine stages and 44 ordered course IDs/titles/purposes/stage/hours/age-adaptation text/four **module titles only**. Outcomes and module focus were withheld after an automated build gate found they duplicated correct draft quiz options. No check, option, answer index, explanation, lesson body or user data belongs in public JSON. `python3 scripts/build_public_catalog.py --check` and `npm run verify:release` detect stale/unsafe data and unwanted JS chunks. The source master remains a **draft**, not a published question bank.

## Future migration order (not yet implemented)

1. Approved verified adult identity/recovery, reviewer MFA, scoped sessions and retention/erasure before external adult enrolment.
2. Organisation/tenant and school/staff membership with all queries tenant-scoped, DB constraints/RLS where appropriate and cross-tenant tests **before** school imports.
3. Qualified-approved age/guardian authority/consent/version/withdrawal state machine and operational safety review **before** creating minor records; never repurpose the disabled 003 hold as consent proof.
4. Reviewed, access-controlled assessment bank/published course releases and durable credentials separate from draft answers; explicit migration policy for in-progress versions.
5. After separate contracts/privacy approval and real provider verification, reconcile AI-01's *synthetic-only* estimates with provider-native metering and introduce an approved physical retention/erasure/restore policy; add real-user AI records only after moderation/safeguarding review. General uploads/object ACLs (beyond the local PNG-only project-core experiment), payment ledger/idempotency, referral attribution and message/notification events remain future work.
6. Conflict-aware offline operation IDs/reconciliation and capped local store, with server verification before progression; then privacy-safe aggregates.

Every migration needs an additive/rollback review, data ownership, idempotency, backup/restore test and a restriction against running disposable test `TRUNCATE` on Railway. See [architecture](ARCHITECTURE.md), [permissions](ROLES_AND_PERMISSIONS.md) and [operations](OPERATIONS.md). Database-owner audit mutation remains possible; independent log retention and restricted DB roles are not implemented.
